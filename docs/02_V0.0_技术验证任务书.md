# AI 智能陪伴桌宠｜V0.0 技术原型验证任务书

- 文档版本：V0.0 Task v1.1（第 34 轮 MiniMax 执行版）
- 当前状态：**第 34 轮已授权向 MiniMax 下发 V0.0 验证任务；不得进入 V0.1**
- 关联：`01_PRD_v1.1_冻结基线.md`

## 1. 阶段目的

在不提前锁定技术栈的前提下，使用相同角色测试资源和相同测试情境，比较至少两条合理的 macOS 桌宠实现路线，选择能稳定支持透明桌面角色、输入事件、2D 动画、扩展角色包和长期运行的技术基线。不得以简单截图或示意页面代替真正可运行的桌面原型。

**候选路线**（按可行性选择至少两条完整验证，必要时补充）：
- Swift + AppKit + SpriteKit（原生）
- Tauri 2 + Rust + 前端 2D 渲染方案（如 PixiJS）
- Electron + React + PixiJS
- 原生桌宠窗口 + 可移植核心模块（适合前三者均不能同时满足关键约束时补充）

不得因为候选语言熟悉度或个人偏好而跳过关键风险测试。技术栈最终由真实验证结果决定。

## 2. 原型必须完成的通用场景

| ID | 场景 | 必须展示的结果 | 必须保留的证据 |
|---|---|---|---|
| T01 | 透明桌面角色 | 桌面可见 Q 版角色，背景透明，窗口可关闭 | 可执行产物、操作录屏、代码位置 |
| T02 | 鼠标交互与穿透 | 点角色可响应；透明空白区域尽量不拦截其他应用 | 交互录屏、系统版本、已知限制 |
| T03 | 基础动画 | 同素材播放待机、行走、跳跃或落地、拖动等少量真实动作 | 动作素材包、动画帧率/播放日志 |
| T04 | 拖拽与边界 | 抓取、拖动、松手、边界约束及基本物理响应 | 录屏、边界异常清单 |
| T05 | 层级与焦点 | 置顶/非置顶策略可控，不抢占其他软件键盘焦点 | 场景录屏、操作步骤 |
| T06 | 多屏与 Spaces | 接入外接屏/不同桌面空间或记录设备不具备的情况 | 实测矩阵、未覆盖说明 |
| T07 | 空闲负载与前台工作 | 前台处理普通工作和高负载应用时，记录 CPU、内存和帧耗时 | 原始测量表与工具名称 |
| T08 | 异常恢复 | 角色素材缺失/窗口关闭/多次启动退出不造成无法恢复的异常 | 失败用例、日志、修复记录 |
| T09 | 资源接口演示 | 可用声明式元数据替换一套测试动作素材而不改动运动逻辑 | 资源规范草案、导入演示 |
| T10 | 安全边界 | 原型默认不请求截图/麦克风权限，不写入真实 API Key | 权限核对与静态检查结果 |

**统一测试素材**：所有候选原型使用同一组拥有使用授权的 PNG/Sprite Sheet，动作定义、角色展示大小、渲染目标尽量一致。无合规素材时可使用原创几何测试角色，但须注明不能据此评估最终美术品质。

## 3. 测量方法与目标

1. 所有结果标明机器型号、芯片、内存、macOS 版本、分辨率、接屏情况、测试工具、构建号和录制时间。
2. 测试冷启动、10 分钟交互、30 分钟持续活动、10 分钟低功耗空闲、重复启动退出 20 次；如设备/环境受限，逐项标明未执行，不得宣称通过。
3. 至少记录：冷启动至可交互时长、常驻内存峰值与典型值、CPU 占用、动画 FPS 与帧耗时分布、窗口焦点/鼠标穿透异常次数、错误日志。
4. 第 28 轮提出的 5 秒启动、30 FPS、250 MB 空闲内存、低于单核心 5% 待机 CPU 均为**参考目标**。V0.0 要先测试可行性并提出正式门槛，不能写成实测成绩。
5. 24 小时运行测试保留为 V1.0 发布验收的重要要求，不把它与 V0.0 的短期验证混为一谈。

## 4. 技术评估与否决规则

**硬性否决事项**
- 无法在实际 macOS 桌面显示透明、可退出的交互角色。
- 无法可靠操作桌面角色，且没有合理可验证的输入事件方案。
- 为了关键特性必须引入不可接受的隐私、系统完整性或代码执行风险。
- 无法给出可重复构建步骤或真实运行证据。

**通过硬性门槛后进行权重比较**

| 维度 | 权重 |
|---|---:|
| 透明窗口、鼠标与焦点行为 | 25% |
| 2D 动画、动作控制与扩展资源支持 | 20% |
| CPU/内存/流畅度与稳定性 | 20% |
| MiniMax 可维护性、模块化及可测试性 | 15% |
| 未来 Windows 可移植性 | 10% |
| macOS 构建、签名/分发可行性 | 10% |

每项打 1～5 分、附测试证据与不确定性。分数只作为辅助决策，安全及关键运行问题不允许被总分掩盖。若结果接近，优先选复杂度更低且长期维护更清晰的方案。

## 5. 允许与禁止的操作

**本次 V0.0 授权范围内允许：**在独立 V0.0 工作目录创建可运行原型、测试角色包、自动测试脚本与报告；修复原型问题；记录工程依赖；在阶段内迭代和复测。

**未经单独授权禁止：**
- 进入 V0.1 或制作完整 AI 聊天、记忆、复杂多角色系统。
- 处理或上传真实私密聊天、真实 API Key、用户文件、敏感系统数据。
- 覆盖用户现有项目、删除历史工程，或在不通知的情况下改变 PRD 已冻结的目标。
- 将没有真实设备验证的技术指标写成 PASS。
- 替用户发布软件、上传代码到公共仓库或开通付费服务。

## 6. 阶段交付包清单

- 至少两条候选方案的代码和各自可重复构建说明。
- 能在测试环境运行的原型程序或构建产物（注明实际可执行平台）。
- 同一测试资源包及资源许可说明。
- `PROTOTYPE_TEST_REPORT.md`：逐项 T01～T10 的 PASS/PARTIAL/FAIL、日志与截图/视频定位。
- `PERFORMANCE_BASELINE.csv`：有采样条件、单位、原始数值、未测缺失说明。
- `TECH_DECISION.md`：对比矩阵、评分、风险、建议技术栈和备选方案。
- `KNOWN_ISSUES.md`、`README.md`、`HANDOVER.md`、`CHANGELOG.md`。
- Git commit / tag、阶段独立备份与校验结果，且不存在密钥和私密资料泄露。

## 7. V0.0 结束判定

- `PASS`：核心桌面行为在目标 Mac 实测通过，至少两条候选获得可比较数据，安全无阻断，技术选型理由可核查；批准候选技术栈进入下一轮评审。
- `PARTIAL`：部分行为或测量尚未验证、存在可修复问题或覆盖不足；只汇报结果，不冻结技术栈。
- `FAIL`：关键交互不可行或存在不可接受风险；提出改造路线后由用户决定是否扩大技术验证范围。

> **第 34 轮用户已要求向 MiniMax 下发 V0.0 开发/验证指令；不得将此视为 V0.1～V2.0 的启动授权。**


## 8. 第 34 轮补充：逐项可核查的验收口径

| 测试 | PASS 标准 | PARTIAL / FAIL 标准 |
|---|---|---|
| T01 透明桌宠 | 真实 macOS GUI 中运行，背景透明，角色清晰，用户可关闭、无残留僵尸进程 | 只在浏览器/截图显示为 PARTIAL；崩溃或无法绘制 FAIL |
| T02 命中/穿透 | 点击实体触发互动；点透明区域落到下层应用；两者切换无明显丢输入，重复 20 次 | 只有整窗穿透/实体不能点击 = PARTIAL；持续阻断正常鼠标操作 = FAIL |
| T03 多帧动画 | 至少待机/行走/跳跃或落地/拖拽四类动作按真实帧序播放，可演示事件切换 | 只有静态贴图或硬编码演示帧 = PARTIAL/FAIL |
| T04 拖拽/边界 | 可抓取、移动、释放并停在有效屏幕范围内，重复 20 次不失控 | 偶发越界/焦点丢失 PARTIAL；无法操作 FAIL |
| T05 焦点 | 普通编辑器中持续输入时，桌宠待机不抢键盘焦点；主动操作角色后恢复可用 | 影响常用快捷键/编辑输入 FAIL |
| T06 多屏/Spaces | 实际设备接屏/切换空间验证并记录坐标与层级行为 | 无设备/权限 = NOT_TESTED，绝不自动 PASS |
| T07 性能 | 具备可复核采样原始值、场景、机器信息和统计口径；两候选可比较 | 空白表/主观评价 = PARTIAL；造假 FAIL |
| T08 恢复 | 缺图、坏配置、重复开关 20 次具备有意义的错误处理、不遗留窗口进程 | 未做故障注入 = PARTIAL |
| T09 资源接口 | 不改引擎源码，可替换 manifest 指向的原型动作序列，验证播放 | 修改硬编码路径才能换图 = PARTIAL |
| T10 安全 | 不读取私密文件/音视频/屏幕，不上传数据，不记录密钥，无未声明的权限请求 | 发生未授权访问或数据泄露 = FAIL |

**状态规则**：`PASS` = 在真实可执行目标环境中提供证据；`PARTIAL` = 已实现但不完整或测试覆盖不足；`FAIL` = 关键条件违背；`NOT_TESTED` = 未执行或缺少设备权限。`NOT_TESTED` 不得在阶段汇总时视为 PASS。

## 9. 执行环境分支和证据真实性

- 先识别 `uname -a`、`sw_vers`、`xcodebuild -version`（若存在）、`git status`、`pwd`。
- 若处于真实 macOS GUI 且具备可用工具：实际构建、运行、采样、记录证据，并尽可能完成所有可执行 T01～T10。
- 若是 Linux/远程无 GUI/CI：允许实现和静态/单元测试，但 T01、T02、T04～T07 的真实桌面表现必须列为 `NOT_TESTED`，单列 `MAC_MANUAL_TEST_PLAN.md`，最终阶段判为 `PARTIAL`，不得假造 macOS PASS。
- 禁止在没有用户确认的情况下索要管理员密码、开启屏幕录制/辅助功能、安装系统级常驻服务或购买第三方服务。可以明确提示用户需要手动执行的权限/现场验收步骤。
- 在候选之间使用相同的测试图集，保持画面尺寸、帧数、窗口尺寸、目标 FPS、固定交互脚本一致。对环境导致的无法控制变量应在结果表如实披露。
- 无 Developer ID 证书可以交付本机开发构建，但报告明确标注“未签名/未公证”。

## 10. 交付时必须附上的最小验收证据

1. `TEST_EVIDENCE_MATRIX.csv`：T01～T10，每候选一行，状态、平台、命令、原始证据路径、问题编号和测试时间。
2. `PERFORMANCE_RAW.csv`：时间戳、候选、设备、场景、CPU 指标口径、RSS/峰值、FPS 和帧时（P50/P95），没有数据填 N/A 及原因。
3. `TECH_DECISION.md`：权重评分加硬否决检查；如两种方案都不满足安全/输入核心条件，不得硬选。
4. `MANUAL_MAC_TEST_PLAN.md`：鼠标点击空白区域/角色、焦点、Spaces、多屏、负载、截图/录屏的人工复测步骤；不要求用户公开私人屏幕。
5. `V0_0_FINAL_REPORT.md`：实际完成、失败及未测项、选型建议、风险清单、构建步骤、Git hash、备份校验、下一步授权请求。

## 11. 阶段结束判定补充

即使代码已经写完，缺少 macOS 真机实测时，`ROUND_STATUS=PARTIAL`，`V0_0_STATUS=PARTIAL_NOT_FROZEN`，`TECH_STACK_STATUS=PROVISIONAL`。必须把待补测项逐条列明，**不得冻结技术栈**。若通过全部硬门槛、至少两候选拥有可比较证据，则 V0.0 可标 PASS，同时仅提出推荐技术栈，由用户授权后进入 V0.1。
